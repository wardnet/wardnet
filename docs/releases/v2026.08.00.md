# Wardnet 2026.08.00

The first stable release since [`2026.07.01`](v2026.07.01.md), and the largest feature cycle to date.

Four things are new at the surface. **Private DNS** encrypts the DNS traffic of individual devices — on the LAN and while roaming — so a granted phone keeps using your filtering and your blocklists from anywhere. **Domain routing profiles** let you send named domains down a chosen tunnel (`*.netflix.com` → the UK tunnel) from the gateway, with nothing installed on the device. **DNS analytics** turn the query log into something readable: which trackers are actually talking, how the week compares to the last one, and which device is doing the talking. And **device identification** stops presenting a LAN full of `Randomized MAC` rows — devices are now searchable, hedged manufacturer guesses are shown with the observation behind them, and a Bluetooth address pasted from a vendor app finds its Wi-Fi neighbour.

Underneath, a Go SDK and a rewritten `wctl` CLI ship alongside the JavaScript SDK, the recovery and watchdog plumbing was found to be silently disarmed on real hardware and fixed fleet-wide, and a live gateway whose database had grown to 2.15 GB traced back to two independent bugs that are both closed here.

> [!IMPORTANT]
> **Stopping the daemon now tears down its own kernel state.** Until this release, `systemctl stop wardnetd` left the `inet wardnet` nftables table and the `wg_ward*` interfaces in place — a stopped daemon was still filtering your traffic until the next reboot. It now removes them on a stop signal (but deliberately *not* on its own restarts, so auto-update does not churn your tunnels). If you have scripts or habits that assume rules survive a stop, they will not any more. There is also a real `wardnetd uninstall` now, plus a generated `/usr/local/sbin/wardnet-uninstall` escape hatch.

> [!IMPORTANT]
> **API consumers: `GET /api/system/errors` changed shape.** It used to return scraped log lines (`{ level, target, message }`) and now returns structured diagnostics (`code`, `severity`, `component`, `message`, `hint`, `timestamp`). Anything reading that endpoint directly needs updating; the SDKs already are.

## Improvements

### Private DNS — encrypted DNS for individual devices, on the LAN and roaming

Grant a device Private DNS and it gets its own secret hostname under your Wardnet domain, served over DNS-over-TLS on `:853`. On the LAN, split-horizon points that hostname straight at the Pi; away from home, it rides the reverse tunnel, so a roaming phone keeps your resolver, your blocklists, and your per-device attribution instead of falling back to its carrier's DNS. iOS gets a signed `.mobileconfig` profile; Android gets the hostname plus per-platform setup steps and a copy button. Grants are per-device and revocable, the resolver is closed (only granted hostnames are served), and the feature is Premium-gated with a persisted disable if entitlement lapses. DoT-only for now.

Landed across [#970](https://github.com/wardnet/wardnet/pull/970) (grants + the `:853` listener), [#1010](https://github.com/wardnet/wardnet/pull/1010) (API, signed iOS profile, JS SDK), [#1020](https://github.com/wardnet/wardnet/pull/1020) (relaying `:853` through the reverse tunnel), [#1041](https://github.com/wardnet/wardnet/pull/1041) (admin UI, user PWA page, onboarding push) and [#1101](https://github.com/wardnet/wardnet/pull/1101). Design: [ADR-0029](../adr/0029-private-dns-dot.md).

### Domain routing profiles

Per-domain routing rules — "`*.netflix.com` goes down the UK tunnel" — grouped into **profiles** and assigned to devices in priority order. Wardnet enforces the rule at the gateway, from the DNS answer, so nothing has to be installed on the device: it works for TVs, consoles, and anything else that will never run a VPN client. Closes [#241](https://github.com/wardnet/wardnet/issues/241) via [#1040](https://github.com/wardnet/wardnet/pull/1040).

### DNS query analytics — top trackers, week-over-week, per-device

The DNS page grew the analytics the query log was always capable of supporting: blocked queries labelled by the company behind them (Google, Meta, Criteo, …) from a curated catalogue, week-over-week comparison, and per-device query volume keyed on the stable device id so a DHCP reassignment doesn't fragment the series. Top-N rankings now honour the selected window instead of silently ranking only the last day. Closes [#265](https://github.com/wardnet/wardnet/issues/265) via [#1009](https://github.com/wardnet/wardnet/pull/1009).

### Devices you can actually identify

A LAN view where most rows read `Randomized MAC` isn't an inventory. Three things changed: placeholder IEEE registrations (`Private`, registry filler) are dropped at build time so an unknown manufacturer reads as unknown rather than as a vendor named "Private"; randomization is now a flag on the device rather than a value in the manufacturer column; and searching for a MAC copied out of a vendor app finds the device even when that app reported its Bluetooth address instead of its Wi-Fi one. The device detail view shows the passive signals behind a guess (DHCP options 12/55/60, mDNS services, open ports), so "Likely Govee" comes with the observation that produced it. [#1110](https://github.com/wardnet/wardnet/pull/1110) and [#1118](https://github.com/wardnet/wardnet/pull/1118); design in [ADR-0025](../adr/0025-device-identification.md). Nothing probes a device without a direct admin action.

### A smart-home preset for cross-zone control

Zone isolation made Wi-Fi smart-home gear unreachable from the phone that controls it, and neither shipped preset covered it — a `Casting` exception expands to mDNS and Cast ports, while Govee's LAN API is UDP 4001–4003. A third **Smart home** preset covers the traffic model those appliances actually use: client-initiated unicast control of a LAN appliance, no media stream. Closes [#1098](https://github.com/wardnet/wardnet/issues/1098) via [#1137](https://github.com/wardnet/wardnet/pull/1137).

### Cross-zone casting for tunnel-bound devices

Casting from a phone in one zone to a TV in another failed whenever the phone was bound to a tunnel: the SYN was policy-routed up the WireGuard interface and never reached the forward chain where the casting rules live. Fixed with per-exception switchback rules that return that traffic to local delivery, stateful return so the reply stream survives isolation, and un-NAT so sender-push flows like screen mirroring see the sender's real IP. [#973](https://github.com/wardnet/wardnet/pull/973).

### Go SDK and a rewritten `wctl`

`wardnet.network/go` is a new Go SDK — a hand-written public API over an OpenAPI-generated internal client, with typed errors and clean sum types for the daemon's tagged unions — and `wctl` is now a Go CLI built on it, with tabular output by default and `--json` on all 19 commands. [#1049](https://github.com/wardnet/wardnet/pull/1049) and [#1113](https://github.com/wardnet/wardnet/pull/1113), closing [#229](https://github.com/wardnet/wardnet/issues/229).

### Structured diagnostics instead of scraped log lines

The dashboard's "Recent errors" panel used to grep WARN/ERROR out of the tracing pipeline, which meant plenty of noise reached it and a bare message string offered no guidance. Components now raise typed diagnostics carrying a stable code, severity, component, plain-language message and an admin-facing remediation hint, and the card renders the hint next to the error. [#1013](https://github.com/wardnet/wardnet/pull/1013).

### Authoritative reverse DNS for private ranges

PTR lookups for private IPv4 ranges are answered on the gateway instead of being forwarded upstream, and the per-client rate limiter now applies only to the upstream-bound path. Two mesh nodes emitting ~1,900 PTR lookups each per ten minutes were being rate-limited into REFUSED answers, which made them retry — a self-sustaining flood that is now simply answered. [#979](https://github.com/wardnet/wardnet/pull/979).

### Logs that reach journald

The unit set `StandardOutput=journal`, but a console layer was only attached under `--verbose`, so `journalctl -u wardnetd` showed nothing but systemd's own start/stop lines — which is how a blocklist that had been failing for hours went unnoticed. Production logging now emits a deliberately narrow slice (level *and* target, ~150 lines/day on a real gateway: slow-query warnings, routing, route monitoring) rather than the ~30k lines/day a plain level filter would produce. Part of [#1102](https://github.com/wardnet/wardnet/pull/1102).

## Bug fixes

### The database could grow without bound and never shrink

A live gateway reached 2.15 GB and would not come back down. Two independent causes: the blocklist cron re-dispatched the same refresh every 60 seconds for the whole ~2.5-hour duration of a large import, so a 2.16M-domain feed was imported and deleted dozens of times a day; and the daily reclaim was capped at 2,000 pages (8 MiB) against ~110k pages freed per duplicate import, so free space could only ratchet upwards — 38% of the file was space that could never be returned. Refreshes are now collapsed rather than merely serialised, and the daily pass drains the freelist in chunks instead of stopping after one. A failing feed also backs off instead of re-downloading ~50 MB every minute. An already-inflated database returns its space over the following daily runs. [#1102](https://github.com/wardnet/wardnet/pull/1102).

### The watchdog and crash-loop safety nets were silently disarmed

A post-power-outage investigation on a live Pi found three of the documented recovery mechanisms were not actually armed: `StartLimit*` keys sat in `[Service]`, where systemd ignores them; `/dev/watchdog` is `root:root 0600` and the daemon runs unprivileged, so the hardware watchdog could never open it; and unit-file fixes never reached existing installs because the update tarball carries only binaries. All three are fixed through post-upgrade migrations, so they converge on auto-updated boxes and not just on fresh installer runs. Watchdog status is also reported honestly now — "another supervisor owns it" is a normal state on Raspberry Pi OS, not a fault. [#1028](https://github.com/wardnet/wardnet/pull/1028).

### Member isolation broke addressing on the LAN

Enabling member isolation on any zone set interface-wide `proxy_arp` on the LAN interface, which made the Pi proxy-reply for essentially any address a device probed: macOS reported duplicate IPs on a device's own gratuitous ARP, DHCP fell into decline/retry loops, manual addresses were rejected, and same-LAN peer traffic was pulled into a tunnel table with no LAN routes. Meanwhile the case it was meant to serve never worked, because plain `proxy_arp` doesn't answer same-interface lookups. Replaced with per-member proxy-neighbour entries. Closes [#1107](https://github.com/wardnet/wardnet/issues/1107) via [#1109](https://github.com/wardnet/wardnet/pull/1109).

### A restored backup could change the machine's deployment posture

Restoring a bundle replaced `/etc/wardnet/wardnet.toml` wholesale, which put deploy-time-only settings within reach of an admin session — including `allow_edge_channel` (which ADR-0023 requires root *on that box* to set) and `manifest_base_url` (repoint it at a server that publishes nothing and the box silently stops patching itself while the UI still reports healthy). Those keys are now always taken from the live machine. A bundle restores your data and settings, never the deployment posture of the host it lands on. Closes [#1112](https://github.com/wardnet/wardnet/issues/1112) via [#1141](https://github.com/wardnet/wardnet/pull/1141).

### Security and correctness hardening

- A malformed DHCP packet with an out-of-range hardware-address length could panic the DHCP server loop; the length is now bounded ([#955](https://github.com/wardnet/wardnet/pull/955)).
- WireGuard `private_key` and `preshared_key` no longer appear in `Debug` output ([#954](https://github.com/wardnet/wardnet/pull/954)).
- CORS handling, `DHCPRELEASE` authorization and DNS stats-label escaping hardened ([#1045](https://github.com/wardnet/wardnet/pull/1045)).
- Logging out now revokes the session server-side ([#969](https://github.com/wardnet/wardnet/pull/969)).
- Admin authorization guards added to the DNS, DNS-filter, device-discovery, log and stats service methods ([#1008](https://github.com/wardnet/wardnet/pull/1008), [#982](https://github.com/wardnet/wardnet/pull/982), [#966](https://github.com/wardnet/wardnet/pull/966)).
- Two outstanding RustSec advisories resolved ([#971](https://github.com/wardnet/wardnet/pull/971)).

### Routing, tunnels and DNS correctness

- Deleting a tunnel now resets the default routing policy that pointed at it ([#968](https://github.com/wardnet/wardnet/pull/968)).
- `TunnelInterface::remove` actually deletes the WireGuard interface ([#958](https://github.com/wardnet/wardnet/pull/958)).
- The `zone_isolation` jump rule is no longer reconciled away ([#961](https://github.com/wardnet/wardnet/pull/961)).
- Device IP lookup is deterministic, and a departing device's IP is cleared ([#975](https://github.com/wardnet/wardnet/pull/975)).
- Cached DNS TTLs age on hit, and cache eviction is O(1) at capacity ([#965](https://github.com/wardnet/wardnet/pull/965)).
- Stale datagrams are drained and timed-out conditional-forward sockets dropped ([#1023](https://github.com/wardnet/wardnet/pull/1023)).
- The DNS-events SSE stream detects client disconnect instead of looping ([#1029](https://github.com/wardnet/wardnet/pull/1029)).
- The WAL is bounded, with a checkpoint and `ANALYZE` in daily maintenance ([#978](https://github.com/wardnet/wardnet/pull/978)).
- The post-upgrade runner heals null state arrays and surfaces artifact read errors ([#964](https://github.com/wardnet/wardnet/pull/964)).
- Structured log fields are interpolated into the message rather than dropped ([#1037](https://github.com/wardnet/wardnet/pull/1037)).
- The OpenAPI spec matches runtime nullability, auth schemes and tags; `/api/stats` parameters are correct and `operationId`s are unique ([#962](https://github.com/wardnet/wardnet/pull/962), [#1047](https://github.com/wardnet/wardnet/pull/1047)).
- Admin-site mutation and display-correctness fixes ([#1025](https://github.com/wardnet/wardnet/pull/1025)); user-app DNS-stats stale-date race and unbounded daily store growth ([#1022](https://github.com/wardnet/wardnet/pull/1022)); SDK DNS log-stream reconnect now backs off with jitter ([#1024](https://github.com/wardnet/wardnet/pull/1024)).
- DNS hot-path optimizations and streamed blocklist loading ([#980](https://github.com/wardnet/wardnet/pull/980), [#1011](https://github.com/wardnet/wardnet/pull/1011)).

## Upgrading

### Auto-update (recommended)

Open **Settings → Updates** in the admin UI and apply the update — the daemon binary swap is mediated by the root-owned post-upgrade runner. The watchdog, crash-loop and unit-file fixes in [#1028](https://github.com/wardnet/wardnet/pull/1028) ship as post-upgrade migrations, so they reach auto-updated boxes without an installer run.

Note the callouts above before upgrading:

- A `systemctl stop wardnetd` now removes the `inet wardnet` nftables table and the `wg_ward*` interfaces. This is deliberate, and self-initiated restarts (auto-update, rollback, admin Restart) are exempt.
- If you consume `GET /api/system/errors` directly, update to the new diagnostics shape.

An inflated database needs no operator action — the daily maintenance pass now returns free pages to the filesystem over subsequent runs.

### Manual installer

```sh
curl -sSL https://wardnet.network/install.sh | sudo bash
```

### Uninstalling

```sh
sudo wardnetd uninstall --dry-run  # print everything that would be removed
sudo wardnetd uninstall            # stop, disable, and remove runtime state
sudo wardnetd uninstall --purge    # also delete /var/lib/wardnet — unrecoverable
```

Both destructive forms prompt for confirmation; pass `--yes` to run them non-interactively. Design: [ADR-0028](../adr/0028-shutdown-teardown-and-uninstall.md).

## Targets in this release

| Target | Architecture |
|--------|-------------|
| Raspberry Pi (3 and newer) and other `aarch64` Linux SBCs | `aarch64-unknown-linux-gnu` |
| Mini-PCs, `x86_64` servers, and other non-Pi Linux hosts | `x86_64-unknown-linux-gnu` |

Wardnet needs a 64-bit OS — there is no 32-bit (`armv7`) build. On a Raspberry Pi, use the 64-bit Raspberry Pi OS.
