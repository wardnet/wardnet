# Wardnet 2026.07.00-beta.3

Patch beta following [`2026.07.00-beta.2`](v2026.07.00-beta.2.md). The headline: the **Network Zones lockout is fixed** — the known issue that shipped as a warning on beta.2 is closed, with three independent guards so no single regression can reopen it. Alongside it: re-enrolling remote access with a name you already own now **joins your existing network** instead of failing with "already taken", updates report their outcome honestly (no more phantom PENDING version), and a failed certificate issuance retries in seconds instead of half a day. Beta builds receive updates via the **beta channel** only — switch to it in **Settings → Updates** to opt in.

> [!IMPORTANT]
> A fresh, ground-up beta install is supported with `curl -fsSL https://wardnet.network/install.sh | sudo CHANNEL=beta bash`. The installer's `CHANNEL` only selects **which tarball is fetched** — the daemon's auto-update channel is stored separately and still defaults to `stable`. After a fresh beta install you **must** set the channel to `beta` in **Settings → Updates**, or the box will not receive further beta updates. It will not downgrade; it will simply sit on this build.

## Bug fixes

### Network Zones can no longer lock you out of your gateway

The beta.2 known issue is fixed. If the device inventory held a record claiming the Pi's **own LAN address** (a proxy-ARPing Wi-Fi/powerline bridge can genuinely answer for it), moving devices into an isolation zone made the daemon enforce network policy against itself — deleting the kernel route that delivers the Pi's address *to the Pi* and cutting off the admin UI, SSH and ping from every device, over every path. Recovery required physical access.

Three independent guards now stand in the way, any one of which would have prevented the incident: route removal can no longer touch the kernel's own `local` routing table; zone enforcement refuses to act on any address the gateway itself owns (the LAN IP and every per-zone gateway alias), at every entry point including startup; and device discovery refuses to record the gateway's own IP — and stops trusting a device that claims several different addresses within a minute, which is how the bad record was born. A poisoned record left over from an earlier version is repaired automatically at startup. Closes [#886](https://github.com/wardnet/wardnet/issues/886).

### Updates no longer report a phantom pending version

After a successful auto-update the daemon kept reporting the new version as *pending* forever — the marker was set before the restart and nothing on the way back up ever settled it. The daemon now reconciles the marker at boot: a completed swap is stamped as **Applied** (and the UI toasts "Wardnet updated to v…"), a silently reverted swap is surfaced as **Failed** naming both versions, instead of the box quietly running the old binary with a stale claim. Closes [#889](https://github.com/wardnet/wardnet/pull/889).

### "Send code" tells you what's wrong instead of doing nothing

In remote-access enrollment, clicking **Send code** with a missing or malformed email did nothing at all — the button silently swallowed the click. It now validates the address and reports the problem through the normal error path, in both the Settings flow and the setup wizard. Closes [#889](https://github.com/wardnet/wardnet/pull/889).

### A failed certificate issuance retries in seconds, not 12 hours

Certificate issuance can fail transiently right after registration (the cloud publishes the new hostname's DNS record a few seconds after the daemon reports its IP — losing that race is expected). The TLS runner treated any failure as "try again at the next 12-hour tick", so a lost 10-second race cost half a day without a certificate. Failures now retry on a short exponential backoff (30 s doubling, capped at 15 min), returning to the 12-hour cadence on success. Closes [#889](https://github.com/wardnet/wardnet/pull/889).

## Improvements

### Re-enrolling with your own name joins your existing network

Re-registering remote access with a hostname your account already owns used to dead-end with "'name' is already taken" — your own network held the name and there was no way back in. Registration now **adopts** the existing network: the daemon joins it, the network's region and settings win, and the UI says so ("Joined your existing network …"). A reflashed box joins even at the plan's device limit — its stale registration on that network is displaced — and a box that only lost its local configuration re-joins idempotently. Deleting a network and immediately reusing its name now also tells the truth ("being deleted — retry in a few minutes") instead of a generic conflict. Daemon side in [#890](https://github.com/wardnet/wardnet/pull/890); the matching cloud change is wardnet-cloud [#89](https://github.com/wardnet/wardnet-cloud/pull/89).

## Upgrading

### Auto-update (beta channel)

Set the channel to **beta** in **Settings → Updates**, then apply the update as usual. The daemon binary swap is mediated by the root-owned post-upgrade runner.

### Fresh install on the beta channel

```sh
curl -fsSL https://wardnet.network/install.sh | sudo CHANNEL=beta bash
```

Then open the setup wizard at `http://<pi-ip>:7411/admin/` and set the release channel to **beta** in **Settings → Updates** once setup completes (see the note above).

### Manual installer

Re-run the installer to pick up the new daemon:

```sh
curl -sSL https://wardnet.network/install.sh | bash
```
