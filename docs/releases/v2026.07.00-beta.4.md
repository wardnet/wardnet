# Wardnet 2026.07.00-beta.4

Patch beta following [`2026.07.00-beta.3`](v2026.07.00-beta.3.md), focused entirely on **remote access certificate issuance**: the failure that made the very first issuance attempt fail on every fresh enrollment is fixed, a failure caused by Let's Encrypt rate limiting now backs off instead of digging the hole deeper, and the dashboard's DNS resolution check no longer cries wolf on a perfectly healthy setup. Beta builds receive updates via the **beta channel** only — switch to it in **Settings → Updates** to opt in.

> [!IMPORTANT]
> A fresh, ground-up beta install is supported with `curl -fsSL https://wardnet.network/install.sh | sudo CHANNEL=beta bash`. The installer's `CHANNEL` only selects **which tarball is fetched** — the daemon's auto-update channel is stored separately and still defaults to `stable`. After a fresh beta install you **must** set the channel to `beta` in **Settings → Updates**, or the box will not receive further beta updates. It will not downgrade; it will simply sit on this build.

## Bug fixes

### The first certificate issuance attempt no longer always fails

Enabling remote access failed its first certificate issuance essentially every time: the daemon published its ACME DNS challenge records and asked the certificate authority to validate them *immediately*, before the records had propagated through the DNS provider's edge — so the CA looked, found nothing, and failed the order. The daemon now waits out a propagation window after publishing the challenge records before requesting validation, and when a validation still fails it logs the CA's actual per-challenge error (instead of a generic failure) so the reason is visible in the dashboard and logs. Closes [#892](https://github.com/wardnet/wardnet/pull/892).

### Hitting a Let's Encrypt rate limit now backs off instead of making it worse

Repeated issuance failures could trip Let's Encrypt's *"too many failed authorizations"* rate limit (5 per hour) — and the short retry backoff introduced in beta.3 would then burn straight through the remaining budget, keeping the account rate-limited indefinitely. The TLS runner now recognises a rate-limit response and holds off for a full hour before trying again, while other failures keep the short exponential backoff. Changing remote-access settings nudges the runner to retry immediately instead of waiting out the current backoff. Closes [#892](https://github.com/wardnet/wardnet/pull/892).

### The DNS resolution check no longer reports a mismatch on a healthy setup

The remote-access panel's resolution check compared what your hostname resolves to against this box's public IP. With the Wardnet cloud now pointing your hostname at the regional tunnel ingress (rather than publishing your home IP in public DNS — a privacy improvement on the cloud side), that comparison reported a permanent mismatch on a perfectly healthy setup. For Wardnet-managed hostnames the check now verifies the name resolves at all — which proves the DNS chain end-to-end — while bring-your-own-domain setups keep the strict IP comparison, since there the record really is your address. Closes [#894](https://github.com/wardnet/wardnet/pull/894).

## Upgrading

### Auto-update (beta channel)

Set the channel to **beta** in **Settings → Updates**, then apply the update as usual. The daemon binary swap is mediated by the root-owned post-upgrade runner.

### Fresh install on the beta channel

```sh
curl -fsSL https://wardnet.network/install.sh | sudo CHANNEL=beta bash
```

Then open the setup wizard at `http://<pi-ip>:7411/admin/` and set the release channel to **beta** in **Settings → Updates** once setup completes (see the note above).

### Manual installer

Re-run the installer to pick up the new daemon:

```sh
curl -sSL https://wardnet.network/install.sh | bash
```
