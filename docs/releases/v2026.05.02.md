# Wardnet 2026.05.02

A feature-heavy release on top of [`2026.05.01`](v2026.05.01.md). DNS gets a real query log, statistics, and per-device filter profiles; tunnels and devices each get a routed detail page; you can now reboot or shut down the gateway from Settings; and DHCP option-12 hostnames become the primary device identity.

> [!IMPORTANT]
> **Action required when upgrading to `2026.05.02` from `2026.05.00` or `2026.05.01`.** Before this release, the daemon's auto-update applier tried to rename `/usr/local/bin/wardnetd` itself — that path is `root:root 0755`, so the swap silently failed with `EACCES` on every host that hadn't been re-run through `install.sh`. Auto-update is now mediated by the root-owned post-upgrade runner, but the running daemon on your host predates this fix and will hit the same `EACCES` on its first attempt to install `2026.05.02`. Re-run the installer once with `--upgrade-only` to lay down the runner-mediated swap path:
>
> ```sh
> curl -sSL https://wardnet.network/install.sh | sudo bash -s -- --upgrade-only
> ```
>
> `--upgrade-only` is idempotent and does not touch `/etc/wardnet/wardnet.toml`, the database, or the wardnet user. After this one-time recovery, all future auto-updates apply themselves through the runner without operator involvement.

## Improvements

### DNS query log, statistics, and live tail

The DNS server now persists every query under a configurable retention window and surfaces it in three places. A new `/dns/logs` page shows the full log with filter bar, sticky table headers, paginated history, and a live-tail toggle that streams new queries over a WebSocket. The Ad blocking page gains a Stats tab with cards, a brushable time-series chart, and top-domain / top-client panels. The dashboard picks up DNS query and blocked-percentage cards. The hot path uses a non-blocking `try_send` sink and a background runner that batches inserts into SQLite, so the resolver never waits on disk. Closes [#220](https://github.com/wardnet/wardnet/issues/220).

### Per-device DNS filtering with profiles

Ad blocking is now one of three builtin DNS filter profiles (Ad Blocking, Parental Controls, Malware & Phishing) and you can create your own. Each device can opt into a specific profile or fall back to the gateway-wide default, and a per-device kill switch records "would have blocked" queries with a `blocked_skipped` badge in the log. The DNS Filter is exposed as a column on the Devices table, a card on each device's detail page, and a routed `/dns/filter` profile manager. Existing blocklist / allowlist / rules entries are migrated into the Ad Blocking profile automatically. Closes [#221](https://github.com/wardnet/wardnet/issues/221) (and absorbs [#264](https://github.com/wardnet/wardnet/issues/264)).

### Tunnel detail page with throughput chart

Each tunnel now has a routed `/tunnels/:id` page with a metadata block, a brushable throughput chart (5-minute intraday over 48 h, daily over 12 months), a totals callout that follows the brushed window, and the list of devices currently routed through it. The daemon picks up per-tunnel time-series storage with an idempotent rollup + retention runner — `bytes_tx` / `bytes_rx` were point-in-time snapshots before, so there was nothing to plot. Backups ride along automatically (`VACUUM INTO` already snapshots every table). Closes [#96](https://github.com/wardnet/wardnet/issues/96).

### Routed `/devices/:id` detail page

The device-edit sheet has been replaced with a routed detail page. Three feature cards — Identity, Settings, and Network — own their own edit state, so changing a device name or routing target no longer pulls the whole form into one giant sheet. The Settings card promotes a discovered device into a managed one in a single Save; the Network card adds, edits, and removes DHCP reservations in place; and the routing picker collapses Direct + per-tunnel options into a single dropdown with country flags. Establishes the convention going forward: routed pages for read-mostly detail views, sheets for forms.

### Safe Reboot and Safe Shutdown

Settings → Power gains Reboot and Shutdown buttons alongside the existing Restart. Both are admin-only, return immediately, and let systemd / logind drive the actual action — the daemon never touches the shutdown token. The progress dialog has a definitive `off` terminal state so a real shutdown shows as "Powered off" instead of indefinite "Reconnecting". A new optional polkit rule (applied by the post-upgrade runner — see [Upgrading](#upgrading)) authorises the `wardnet` user for the `reboot` and `power-off` actions; without it the buttons simply remain inert. Closes [#215](https://github.com/wardnet/wardnet/issues/215).

### DHCP option-12 hostnames as primary device identity

Device hostnames now follow DHCP option-12 first and reverse DNS only as a fallback, so when a client renames itself (e.g. `living-room-tv` → `kitchen-tv`) the change propagates through every page on the next lease renewal instead of waiting for the next packet observation. The DHCP Leases and Reservations tables gain a new "Host" column with the device-type icon, hostname, and MAC laid out the same way the Devices grid is. Closes [#233](https://github.com/wardnet/wardnet/issues/233) and [#87](https://github.com/wardnet/wardnet/issues/87).

### SLSA build provenance for release artefacts

Every release tarball and `openapi.json` shipped from this version forward carries a SLSA build-provenance attestation, signed by the GitHub Actions OIDC issuer and tied to the workflow run that produced the artefact. Verify a downloaded tarball with:

```sh
gh attestation verify wardnetd-<version>-<arch>.tar.gz --owner wardnet
```

minisign signing of the auto-update payload is unchanged. Closes [#277](https://github.com/wardnet/wardnet/issues/277).

## Bug fixes

### Auto-update no longer fails with `EACCES` on `/usr/local/bin/wardnetd`

The daemon used to attempt the `/usr/local/bin/wardnetd` rename in-process. The wardnet user can't write that directory regardless of file ownership — `rename(2)` requires write+x on the destination — so the swap failed silently on every production host that hadn't been re-run through `install.sh` since the daemon was installed. Auto-update is now mediated by the root-owned `wardnet-postupgrade-runner`: the daemon stages a verified tarball + signature into a wardnet-writable directory, the runner re-verifies the staged payload against its embedded public key, and the actual rename happens under root before `wardnetd.service` starts. Rollback follows the same trust path. The first auto-update to `2026.05.02` from `2026.05.00` / `2026.05.01` still needs the one-time `install.sh --upgrade-only` step to put the new applier in place — see [Upgrading](#upgrading). Closes [#309](https://github.com/wardnet/wardnet/issues/309).

### Tunnels recover automatically when their kernel interface disappears

If a `wg_*` interface was dropped — a daemon restart, a manual `ip link delete`, or any other event that pulled the kernel state out from under the daemon — the affected tunnel got stuck in `Reconnecting` forever, and devices routed through it silently fell back to direct. The health-check loop now reconciles DB status against kernel reality: any non-`Down` tunnel whose interface is absent flips to `Down` with a `TunnelDown { reason: "interface absent" }` event, so the existing on-demand bring-up path takes over the next time a routed device sends traffic. Tunnels stuck in `Reconnecting` past 15 minutes are also actively torn down and recreated, so recovery no longer depends on routed-device traffic. Closes [#311](https://github.com/wardnet/wardnet/issues/311).

## Upgrading

### To `2026.05.02` from `2026.05.00` or `2026.05.01`

Two steps:

1. **Bootstrap the runner-mediated update path** — once, on the gateway host:

   ```sh
   curl -sSL https://wardnet.network/install.sh | sudo bash -s -- --upgrade-only
   ```

   `--upgrade-only` is idempotent. It does not touch `/etc/wardnet/wardnet.toml`, the database, or the wardnet user — it only updates the post-upgrade runner with the new auto-update swap logic and the optional polkit rule for Safe Reboot / Safe Shutdown. **Skipping this step means the running daemon will fail with `EACCES` the first time it tries to apply this release**, and Settings → Power will show inert Reboot / Shutdown buttons.

2. **Apply the daemon update.** With the runner in place, auto-update from **Settings → Updates** picks up `2026.05.02` and onwards normally, and every future release applies itself without operator involvement.

After this release, the runner is the durable trust anchor for auto-update — `--upgrade-only` is only required for this one-time `2026.05.0x → 2026.05.02` transition.

### Fresh installs

A first-time `install.sh` already lays down the runner-mediated swap path and the optional polkit rule, so there's nothing extra to do.
